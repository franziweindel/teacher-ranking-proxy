# Student-Specific Teacher Ranking Proxy Benchmark

You are a senior ML research engineer working inside:

```text
/data/cat/ws/frwe188h-otagent/OpenThoughts-Agent-trp
```

Build a small, reproducible research pipeline under:

```text
/data/cat/ws/frwe188h-otagent/OpenThoughts-Agent-trp/data/teacher_ranking_proxy/
```

The research question is:

> Given a target pre-SFT student model (S), trajectories generated by that student (\tau_S), candidate teachers (T_1,\ldots,T_m), and released trajectories generated by those teachers (\tau_T), can we compute a cheap pre-SFT proxy
>
> [
> f(S,\tau_S,T,\tau_T)
> ]
>
> that ranks candidate teachers in approximately the same order as their downstream SFT utility for that student?

The goal is **teacher ranking**, not prediction of exact downstream benchmark scores.

Not every proxy requires student trajectories. For example, likelihood-based metrics can use student weights + teacher trajectories only. The proposed behavioral proxy additionally uses student trajectories.

**Do not run new SFT.** Published teacher-ablation rankings are the ground-truth evaluation labels.

Start with **Terminal-Lego**. Later the same framework should support OpenThoughts-Agent.

## General engineering rules

* Reuse existing OpenThoughts-Agent and Harbor infrastructure wherever possible.
* Do not reimplement vLLM serving, Harbor orchestration, trace export, Hugging Face upload, or task handling if reusable code already exists.
* Before implementing something new, inspect the relevant repository code and, where useful, search for existing public implementations.
* Build reusable scripts; do not perform one-off manual preprocessing that cannot be reproduced.
* All sampling must be deterministic and seed-controlled.
* All stages must be resumable.
* Never silently drop tasks, change models, change container runtimes, or alter experiment definitions.
* Never hard-code API/Hugging Face tokens.
* Do not tune proxy definitions using the published teacher ranking.
* Prefer small smoke tests before expensive runs.

## Deliverables

**Four Python files** under `data/teacher_ranking_proxy/`, each one stage of the
pipeline:

```text
prepare_dataset.py         cheap, network        → task_manifest.jsonl
generate_trajectories.py   expensive, GPU        → student traces
compute_proxies.py         varies by proxy       → per-task proxy scores
evaluate_ranking.py        free, seconds         → rankings + metrics
```

`compute_proxies.py` cost depends on the proxy: teacher-only baselines
(`PROXY_SPEC.md` §2) are CPU text analysis; the likelihood-based published
proxies (§3) run the **student model** over every teacher trajectory and are the
GPU-heavy ones; SCRF (§§4–8) is mostly CPU plus LLM-judge calls.

CLIs and required behavior: `EXPERIMENT_SPEC.md` §15.

`prepare_dataset.py`, `generate_trajectories.py` and `compute_proxies.py` each
accept `--n-tasks/--seed` so a run can start in one command; §3 pins the sampling
algorithm so they cannot disagree.

### How firm these are

**Keep the file count as small as possible — these four are the target.** They
are the four pipeline stages, and the split follows real cost differences, which
is why `compute_proxies.py` and `evaluate_ranking.py` in particular must stay
separate: merging them means re-running GPU-hours of scoring every time a metric
is revised.

Everything beyond that is a **preferred default, not a rule**:

* The dataset registry, task sampling and the runtime diagnostic are folded into
  these four rather than given their own files. Add another file only when it
  genuinely earns its place — and if it does, add it and note why in the report.
  Do not split things out for tidiness alone.
* Prefer passing data between scripts through files on disk (the manifest, the
  sample file, the score files) over importing across them, so each stays
  independently runnable and resumable. A small shared import is fine if it is
  genuinely cleaner.
* File formats (`jsonl` for manifests and scores, `json` for the sample file) are
  suggestions. If Parquet or another format fits better at scale, switch — just
  keep one format per artifact type and record it in the run metadata.

## This host — ZIH Capella (TU Dresden)

The full cluster guide is `.agents/ops/zih/ops.md`; the setup/smoke procedure is
the `teacher-proxy-cluster-setup` skill. Report deviations rather than
rediscovering them silently. This replaces the retired sequoia host notes (dead

**GPUs via Slurm only.** Login/interactive nodes have no GPU access; request an
allocation (untyped gres — `gpu:h100:N` is rejected at submit):

```bash
srun --partition=capella --nodes=1 --ntasks=1 --cpus-per-task=14 \
     --gres=gpu:1 --mem=100G --time=02:00:00 --pty bash -l
```

Nodes are 4× H100-SXM5 94 GB, 2×32-core EPYC 9334, 768 GB RAM, Rocky Linux 9,
x86_64. Never set `CUDA_VISIBLE_DEVICES` yourself — Slurm controls visibility.
Compute nodes have **full direct internet egress** (HF, APIs — no proxy/tunnel).

**Container runtime: Apptainer, no Docker.** The §10 parity comparison runs the
Apptainer half against the committed sequoia Docker baseline
(`runs/<run_id>/parity/`). Overlays must stay on **node-local disk** — the
default `$TMPDIR/harbor_overlays_$USER` is correct; never point
`TRP_OVERLAY_ROOT` at `/data/*` (Lustre breaks apt inside task containers).
Verify per-task cgroup limits per the skill's `limcheck` procedure; if they read
`max`, the Slurm job's own cgroup is the cap — record that in run metadata.

**Shared-FS etiquette (admins flag violations).** Never run `find`, `du`, `df`,
`ls -R`, `ls -l` (recursive/colored) on `/data/*` — use `lfs find`, `lfs df`,
plain `ls`. Login-node processes are killed after 600 s CPU; anything heavier
goes in the Slurm job.

**Allocation budgeting.** A 2 h / 1 GPU allocation covers the n=10 milestone,
but first-time SIF builds from task Dockerfiles can eat a large chunk of it.
Every stage is resumable (`--resume`; completed trials are never redone) — if
the allocation runs out, request a new one and continue rather than restarting.
